Phase 2 : Dockerize ML application

===========================================

Traditional ML Flow:
Dataset -> Train -> Model Evaluation -> Prediction

Production ready ML application:
Saved model -> python app -> REST API -> Automated Test -> Docker Container -> CI/CD
Can be tested, deployed, accessed by clients and maintained consistently.

Why we need Docker ?
- Imagine right now ML application is working on your macbook, but fails on another engineer's laptop that runs it on a Linus/windows server.

Possible reasons of failure:
- Different python versions
- Different versions of scikit-learn or fastapi
- Missing python packages
- Different OS dependencies

Docker helps package your application code, runtime, dependencies and startup instructions into a standardized image.

4 major requirements:
- Dockerfile -> instructions for packaging the ML application
- Image -> packaged reusable application artifact
- Container -> running instance of that image
- Port Mapping -> Makes the API inside the Container accessible from your system

Commands for Docker
1. docker ps = print all running containers
2. docker ps -a = print all active/non-active containers
3. docker build -t cse-mlops .
= build docker image
-t = tag = name of the image
4. docker images = list locally available docker images
5. Start the container :
docker run -d --name iris-ml-api -p 8000:8000 cse-mlops

Phase - 4: MLFlow - Experiment tracking and model registry
=================================================

Why do we need MLFlow ?
- Imagine you train a model multiple times, changing the parameters or data version 
- Without experiment tracking you might end up with files like model_v1.joblib, model_v2.joblib, model_final.joblib.
- MLFlow helps us maintain that record 

Training Experiments
- Model parameters, dataset details and evaluation results

MLFlow tracking
- Records parameters, metrics, run information and model artifacts

MLFlow model registry
- Organize model versions, metadata and lifecycle management

Deployment pipeline 
- Select, validate and deploy approved model version

Four major concepts:
- Experiment - collection of related training runs 
- Run - one execution of training with specific parameters and results
- artifact - saved file produced by a run, such as a trained model or evaluation report
- Model registry - managed catalog of registered models and their versions

Install MLFlow
pip install mlflow

mlflow server --backend-store-uri sqlite:///mlflow.db --host 127.0.0.1 --port 5000

Evaluate and promote model versions
- We will add a validation gate that checks model quality before allowing a model version to be considered for deployment

Promote a validated model using champion alias
- Our FastAPI application loads a model from a local file
- This works for demo purpose, but becomes harder to manage when you have multiple model versions.

- Instead of hardcoding a file path or version, we can assign the alias champion to the model version we want our application to use.
